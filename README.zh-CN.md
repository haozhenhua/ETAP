# ETAP

**Ethernet Traffic Awareness Port（以太网流量感知端口）**

本仓库的愿景，是让实时以太网流量成为大模型的一等输入：模型连续消费二进制流量本身，而不是先把流量写成日志、JSON 或自然语言再塞进上下文。

## 愿景

今天的语言模型默认只吃经过分词的文本。要把网络流量交给模型，常见做法是把报文打成十六进制、写成日志，或整理成 JSON、自然语言描述。这样做密度低、信息损失大，而且会把模型训练成“读文章”，而不是“看流量”。

ETAP 想走另一条路。它把流量观察做成一个面向机器的端口，再通过 ETAP 编码器，把端口给出的高密度列式视图适配到各类大模型的表示空间里。这条数据通路不把流量转换成文本。长期看，ETAP 编码器的角色类似视觉编码器之于图像：流量不必先变成句子，也能被模型直接使用。

端口对外提供两种节奏不同的平面：低频控制面，用来发现能力和建立、调整订阅；高吞吐数据面，用来交付带机器可读模式的**流量观察批次**。批次里有三种相互关联的抽象视图——**报文（packet）**、**解析（parse）**、**流（flow）**——用统一的标识（如 `pkt_id`、`flow_id`）对齐。报文字节放在连续缓冲区里，解析结果是带类型的列，变长字段用偏移和长度表示，有效性位图用来区分“未观察到”和“确定没有发生”。过载时用采样、聚合或丢弃处理，并在批次上报告缺口，而不是阻塞数据面。

编码器是这个仓库的核心目标。第一阶段用轻量适配器，把三种视图投影到模型隐空间（例如 Qwen3.5-2B-Base 的 2048 维），用 `inputs_embeds` 拼进冻结的语言模型，只训练适配器即可先跑通。之后可以按需继续预训练或微调基座，或做成更完整的专用 ETAP 编码器，接到更多基座模型上，而不是改写它们的语言核心。

## 原则

- 模型是流量的连续消费者，不是偶尔读一篇流量报告的读者。
- 数据通路不把流量转换成 JSON、日志或自然语言。
- 对外暴露报文、解析、流三种视图，并用统一标识把它们对齐。
- 接口分成低频订阅控制和高频批次数据；核心对象是流量观察批次。
- 编码结果应对齐到目标模型的隐空间，以便适配各类大模型，而不是绑定某一种提示词格式。

## 现在做到哪一步

仓库里已经有 ETAP 接口的 C 参考实现、接口验证，以及面向 Qwen3.5 的最小适配器和「只训适配器就能先跑通」的说明。参考实现带进程内模拟器 `etap://sim`，不需要网卡也能订阅和拉取批次。真实网卡上的实时流量端口、更深的专用编码器、以及接到更多模型，仍是后续工作。
